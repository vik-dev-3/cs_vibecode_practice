# 0005. CI и путь кода до production

- Статус: Принято
- Дата: 2026-11-05

## Контекст
Нужно, чтобы в `main` и на серверах попадал только проверенный код. Работаем одни, ревьюеров нет. Репозиторий был приватным, а защита веток на бесплатном GitHub для приватных репозиториев не применяется.

## Решение
- **CI** — GitHub Actions (`.github/workflows/ci.yml`): `npm ci` → lint → typecheck → test (Vitest) → build. Экшены закреплены по SHA, токен только на чтение.
- **Репозиторий публичный**, `main` защищён ruleset `protect-main`: только через PR, обязательна проверка `check`, без force push и удаления, без bypass.
- **staging** на Railway автоматически деплоится из `main`.
- **production** деплоится вручную, после проверки staging.
- **Healthcheck** `/api/health` (динамический, не пререндерится): Railway переключает трафик только после ответа 200.

## Альтернативы
- **GitHub Pro** для защиты приватного репо — платно; публичность ничего не раскрывает, секретов в репо нет.
- **Railway «Wait for CI»** — переключатель не появился в интерфейсе; не критично, в `main` и так попадает только код с зелёным CI.
- **Автодеплой production** (из `main` или отдельной ветки) — быстрее, но убирает момент ручной проверки staging; вернёмся, когда появятся E2E-тесты (этап 16).
- **`node --test` вместо Vitest** — без зависимости, но не понимает алиасы `@/` из tsconfig.

## Последствия
+ Сломанный код не попадает в `main`, а значит и на staging.
+ Каждое окружение проверяется healthcheck перед переключением трафика.
− Код публичный: секреты — только в переменных Railway и `.env`, Push protection в GitHub включён.
− Деплой production — ручной шаг, его можно забыть.
