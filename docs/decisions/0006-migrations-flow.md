# 0006. Как создаём и применяем миграции

- Статус: Принято
- Дата: 2026-11-14

## Контекст
Схема базы будет меняться на каждом этапе. Баз четыре: локальная (docker compose), CI, staging и production. Они должны быть устроены одинаково, а изменения — видны на ревью.

## Решение
- Схема — в `src/db/schema.ts`. После правки `npm run db:generate` создаёт SQL-файл в `drizzle/`. Его читают на ревью в PR.
- То, что нельзя описать в TS (расширения, данные), пишем через `drizzle-kit generate --custom`.
- Применяет миграции `npm run db:migrate` (`scripts/migrate.mts`, мигратор из `drizzle-orm`). Каждая миграция идёт в транзакции; применённые записаны в `drizzle.__drizzle_migrations` и повторно не запускаются.
- **CI** применяет все миграции на пустую базу и падает, если схему поменяли, а миграцию не сгенерировали.
- **Railway** запускает `db:migrate` в `preDeployCommand`: если миграция упала, новая версия не стартует, старая продолжает работать.
- Применённую миграцию не правим — только новая миграция поверх.
- Приложение подключается к базе Railway через внутреннюю сеть (`RAILWAY_PRIVATE_DOMAIN`), не через публичный TCP proxy.
- База на Railway — шаблон pgvector (`pgvector/pgvector:pg18`): стандартный Postgres Railway не содержит pgvector.

## Альтернативы
- **`drizzle-kit push`** — меняет базу напрямую по схеме, без файла. Быстро для прототипа, но изменения нигде не записаны, их не видно на ревью и нельзя повторить на другой базе.
- **`drizzle-kit migrate` на проде** — потребовал бы dev-зависимость `drizzle-kit` (и её старый esbuild) в продовом образе.
- **Миграции при старте приложения** — несколько копий приложения запустили бы их одновременно; `preDeployCommand` выполняется один раз до старта.
- **Откат через «down»-миграции** — Drizzle их не генерирует. Откат = новая миграция, отменяющая изменение, или восстановление из бэкапа.

## Последствия
+ Все базы получают одни и те же изменения в одном порядке.
+ Забытая миграция или сломанный SQL ловятся в CI, а не на сервере.
− Миграции применяются к production при ручном деплое автоматически: опасные (удаление, смена типа) — только после бэкапа.
− Миграция и код выкатываются вместе; ломающие изменения схемы делаем в несколько шагов (сначала добавить, потом удалить старое).
